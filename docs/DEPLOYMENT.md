# Deployment guide

> **Status: not deployed.** Nothing has been created on any hosting provider. The files below are
> ready to use; creating accounts and services is a manual step that needs the owner's approval.

## Recommended free-tier setup

| Part | Provider | Config in this repo |
|---|---|---|
| Frontend (static SPA) | **Vercel** (Hobby) — or Cloudflare Pages / Netlify | `frontend/vercel.json` |
| Backend (FastAPI container) | **Render** web service (Free) | `render.yaml` (Blueprint), `backend/Dockerfile` |
| PostgreSQL | **Neon** (Free) | Connection string in `DATABASE_URL` |

### Free-tier limits

Free tiers change often. These are the limits as understood at the time of writing (October 2026); **check each provider's pricing page before relying on them.**

| Provider | Limits | Notes |
|---|---|---|
| **Render Free web service** | Spins down after about 15 minutes without traffic. The next request triggers a cold start of roughly a minute (migrations + seed run on every start, and are idempotent). A monthly cap of free instance hours applies. | Not suitable for production. |
| **Render Free Postgres** | Expires after a limited period. | That's why Neon is recommended for the database. |
| **Neon Free** | Small storage quota per project. Compute auto-suspends when idle, so the first query after idling is slower. | Use the **direct** (non-pooled) connection string. psycopg 3 uses prepared statements, which can conflict with transaction-mode poolers. |
| **Vercel Hobby** | Personal, non-commercial use only. Bandwidth and build quotas apply. | — |
| **LLM providers** | The default `mock` provider costs nothing. Ollama runs locally for free. | Hosted LLM APIs (Groq, OpenRouter, Anthropic …) may bill per token. Never set their keys without understanding the pricing. |

Nothing in this guide requires a credit card for the default (`LLM_PROVIDER=mock`) configuration. Some providers do ask for one at sign-up.

## Step by step (after you approve publishing)

1. **Push the repo to GitHub.** See the README section "Publishing to GitHub".
2. **Database (Neon).**
   1. Create a project and a database named `agentcart`.
   2. Copy the *direct* connection string and change the scheme to `postgresql+psycopg://…?sslmode=require`.
3. **Backend (Render).**
   1. New → Blueprint → select the repository. Render reads `render.yaml`.
   2. When prompted, set:
      * `DATABASE_URL`: the Neon URL from step 2.
      * `CORS_ORIGINS`: your Vercel URL, for example `https://agentcart.vercel.app`. Fill this in after step 4 and redeploy.
   3. `JWT_SECRET` is generated by Render (`generateValue: true`). `ENVIRONMENT=production` disables `/api/docs` and enforces a strong secret.
   4. Verify: `curl https://<service>.onrender.com/api/health/ready` should return `"database":"up"` and `"products":115`.
4. **Frontend (Vercel).**
   1. Import the repository and set **Root Directory** to `frontend`. The framework preset (Vite) is auto-detected.
   2. Set the environment variable `VITE_API_BASE_URL=https://<service>.onrender.com`. It is read at build time.
   3. In `frontend/vercel.json`, tighten `connect-src` from `https://*.onrender.com` to your exact API origin.
   4. Deploy, then add the Vercel URL to Render's `CORS_ORIGINS`.
5. **Smoke test the deployment.**
   1. Register, ask the reference laptop question, approve an add-to-cart, and place a demo order.
   2. **Verify the trusted-proxy setting** (`TRUSTED_PROXY_HOPS`, default 1). Render doesn't document its `X-Forwarded-For` behaviour, so this check confirms the assumption. Repeat it after any change to the hosting setup, such as a custom domain, a CDN in front, or a different provider. These attempts count against your own IP's login budget for one minute.
      1. **Forged addresses must not bypass the limit.** From your machine, send 13 failed logins, each with a different forged `X-Forwarded-For`. `curl` opens a new connection, and therefore a new source port, for every request:

         ```bash
         for i in $(seq 1 13); do curl -s -o /dev/null -w '%{http_code} ' -H "X-Forwarded-For: 203.0.113.$i" \
           -H 'Content-Type: application/json' -d '{"email":"nobody@example.com","password":"WrongPass123"}' \
           https://<service>.onrender.com/api/auth/login; done; echo
         ```

         Expected: ten `401`s, then `429`. The `429` response carries a `Retry-After` header; check with `curl -si` on one more request.
      2. **Other users must keep their own budget.** Within the same minute, send one failed login from a **different network**, for example a phone on mobile data or a hotspot. Expected: `401`, not `429`.
      3. **Interpreting failures:**

         | Result | Meaning | Action |
         |---|---|---|
         | Step 1 never returns `429` | The selected entry is client-controlled. Either the platform forwards the header without appending, or `TRUSTED_PROXY_HOPS` is higher than the real number of appending proxies. | **Don't go live.** Lower `TRUSTED_PROXY_HOPS` if you raised it; otherwise restrict traffic to the platform proxy. |
         | Step 2 returns `429` | More proxies append than configured, so every user shares one budget. This is too strict, not a bypass. | Raise `TRUSTED_PROXY_HOPS` by one, redeploy, and repeat **both** steps. Never raise it past the point where step 1 still returns `429`. |
         | Both as expected | The trusted-proxy setting is correct | None |
   3. Optionally run Playwright against it:

      ```bash
      E2E_BASE_URL=https://<app>.vercel.app npx playwright test --project=desktop
      ```

      This creates test accounts and orders in that database.

## Alternative: single VM with Docker Compose

Any small VM with Docker can run the same stack as local development:

1. Copy `.env.example` to `.env`, generate secrets, and set `ENVIRONMENT=production`.
2. Run `docker compose up -d --build`.
3. Put a TLS-terminating reverse proxy (Caddy, Traefik) in front of port 8080.
4. Don't publish ports 5433 or 8000 publicly. Compose binds them to `127.0.0.1` already.

## Operations notes

* **Migrations** run automatically at container start (`alembic upgrade head`). Roll back with `alembic downgrade -1` from a shell in the container (on Render's free plan, which has no shell, run it locally against the database URL).
* **Migration `0002` (agent tasks)** is additive: it creates `agent_tasks` and `agent_task_steps` and changes no existing table, so it is backward compatible and safe to apply to a live database. Downgrading drops those two tables and the task history in them.
* **Agent tasks** run in the API process after the request returns. A restart or deploy interrupts running tasks; their lease expires after `TASK_LEASE_SECONDS` and users can resume them from the Tasks page. No worker service is needed.
* **Re-seeding** with `python -m app.seed --reset` restores demo prices and stock after demo orders.
* **Logs** go to stdout. Unhandled exceptions are logged with stack traces server-side only.
* **Scaling** beyond one instance needs a shared rate-limit store (see `docs/SECURITY.md`).
